# {App}-TASK-{NNN} — {작업명}

> ⚠ **TEMPLATE** — 모든 `{...}` placeholder를 실제 값으로 채우거나 해당 줄을 삭제한다.
> 본 파일은 단일 App (`{App}`) 의 **작업 범위 계약(Task Spec) 1건** 이다. 결과 파일명과 문서 ID는 `{App}-TASK-{NNN}` 형식을 사용한다.
>
> **TASK 는 Scope Authority**: 이번 작업에서 무엇을 하고, 무엇을 하지 않으며, 어떤 상태가 완료인지 정의한다. TASK 는 영구 SSOT 가 아니며, FRD/FC/ADR/ADR-CATALOG 를 분석하거나 갱신하지 않는다.
>
> **SSOT 책임 분리**: 관련 FRD/FC/ADR 영향 분석과 문서 갱신은 별도 SSOT 작성 단계에서 수행한다. TASK 작성자는 §6 에 입력 근거만 남기고, "어떤 SSOT 를 고쳐야 한다"는 후보 목록을 만들지 않는다.
>
> **Work Packet 전제**: 코드 작업자는 TASK 를 단독으로 받지 않고, 이후 생성되는 Work Packet 을 통해 TASK + 관련 SSOT 링크를 함께 받는다. 코드 실행 시 TASK 는 범위 기준, SSOT 는 진실/제약 기준, Work Packet 은 읽을 문서 라우터다.
>
> **작업 유형 메타**: 메타 표의 "작업 유형" 에 분류를 명시한다 — `feature` / `refactor` / `maintenance` / `migration` / `setup` / `investigation` / 기타. **리팩토링 작업도 본 TASK 양식을 사용** (별도 RFD 양식 폐기됨).
>
> **검증 가능성**: §3 목표 상태·§8 작업 단계·§9 완료 기준·§9.2 엣지 케이스·§9.3 오류 처리는 코드로 관찰·대조 가능한 형태로 작성한다. 코드가 정확히 일치해야 할 literal(예외 메시지·출력 포맷·타입/네임스페이스·설정 키)은 §12.2 에 verbatim 으로 둔다.

| 항목 | 값 |
|---|---|
| 문서 ID | {App}-TASK-{NNN} |
| 버전 | {예: 0.1 (Draft)} |
| 상태 | Draft / Accepted / Superseded / Done / Dropped |
| 작업 유형 | feature / refactor / maintenance / migration / setup / investigation / 기타 |
| 작성 가정 | {본 작업 지시서 작성 시 깔린 가정. SSOT 갱신 완료 가정은 쓰지 않는다} |

> **메타 행 안내**: TASK 는 영구 SSOT 를 직접 링크하지 않는다. 관련 SSOT 링크는 Work Packet 에서 관리한다.
