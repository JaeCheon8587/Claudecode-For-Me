# atelio 진행 기록

이 세션에서 한 작업을 아래 템플릿의 진행 기록 본문으로 정리하고, **사용자가 승인하면** atelio 액션 아이템에 남긴다.

인자: `$ARGUMENTS`
- 첫 토큰이 숫자면 `item_id` 로 본다. 나머지 텍스트는 기록할 내용 메모로 본다 — 세션 대화보다 우선하는 원재료다.
- 인자가 없으면 대상 아이템은 목록에서 고르고, 내용은 이 세션의 대화에서 정리한다.

## 절차

1. **도구 로드** — atelio 도구는 deferred 다. `ToolSearch("select:mcp__atelio__list_action_items,mcp__atelio__get_action_item,mcp__atelio__add_progress_log")` 로 먼저 스키마를 불러온다.
   도구가 하나도 로드되지 않으면 atelio MCP 서버가 등록되지 않은 것이다 — 멈추고 등록 명령을 안내한다:
   `claude mcp add --transport http --scope user atelio https://atelio.site/mcp/mcp` (등록 후 새 세션).
2. **대상 아이템 확정** — id 를 추측하지 않는다.
   - `item_id` 가 있으면 `get_action_item` 으로 제목을 확인한다.
   - 없으면 `list_action_items(limit=20)` 을 조회하고, 이 세션 작업과 제목이 가까운 것을 앞에 두어 `AskUserQuestion` 으로 고르게 한다.
3. **원재료 수집** — 인자의 메모, 이 세션의 대화(맥락 압축 요약 포함), 필요하면 `git log` · `git status`. 대화에 없는 작업을 지어내지 않는다.
4. **템플릿 선택** — 작업 항목마다 고른다.
   - 신규 기능 · 설계 · 분석 → **기능 개발 템플릿**
   - 기존 동작을 바꾸는 개선 · 리팩토링 · 버그 수정 → **기능 개선 템플릿**
5. **본문 작성** — 아래 템플릿과 작성 규칙대로.
6. **식별자 점검** — 본문을 한 줄씩 다시 읽어 금지 식별자가 남았으면 기능 설명으로 바꾼다.
7. **승인** — 대상 아이템(id · 제목)과 본문 전체를 코드 블록으로 보여 주고 `AskUserQuestion` 으로 묻는다: `기록` / `수정` / `취소`.
   - `수정` 이면 요청대로 고쳐 다시 보여 주고 다시 묻는다.
   - `취소` 면 아무것도 쓰지 않고 끝낸다.
   - **승인 없이 `add_progress_log` 를 호출하지 않는다.**
8. **기록** — `add_progress_log(item_id, body)`. 위키 반영은 백그라운드 잡이다 — "완료" 라고 하지 않고 "기록 요청됨(위키 반영 대기)" 으로 보고한다.

## 템플릿

첫 줄은 오늘 날짜(`YYYY-MM-DD`). 작업 항목은 `- ` 로 시작하고, 하위 단계는 4칸 공백 들여쓰기. 최대 3단계.
작업 항목이 여럿이면 날짜 한 줄 아래에 항목을 이어 쓴다. 템플릿 이름(`[기능 개발 ...]`)은 본문에 쓰지 않는다.

### 기능 개발 템플릿 (기능 개발 · 설계 · 분석)

```
2026-10-14
- 장기 공정 데이터의 파티션 정리 대응 기능 개발
    - 2주 이상 변화 없이 유지되는 공정 데이터가 DB 파티션 정리 후 화면에서 사라지는 문제를 방지하기 위해 개발
    - 파티션 키(P_KEY)가 변경되면 모든 라인의 모니터링 캐시 6종을 비워, 다음 수신 데이터를 현재 파티션에 다시 적재하도록 구성
    - 캐시 초기화 직후에는 라인별 설비 정보가 먼저 적재되도록 공정 메시지 적재를 차단하고, 설비 정보 커밋 후 재개
    - 차단 중 공정 메시지는 폐기하고 다음 수집 주기로 보완하며, 300초가 지나면 경고 후 강제 해제
    - P_KEY는 기동 직후 조회하고 이후 24시간마다 확인하며, 최초 기준값 확보에 실패하면 60초 간격으로 재시도
```

- 첫 하위 줄에 **왜** 개발했는지(해결하려는 문제)를 쓴다.
- 이어서 **무엇을 어떻게** 구성했는지를 동작 · 조건 · 수치 수준으로 쓴다.

### 기능 개선 템플릿 (기능 개선 · 리팩토링)

```
2026-10-14
- BM/PM 개발 시나리오 정리 및 기능 개발
    - 개선 전
        - 변경 감지가 직전 주기 대비 증가분만 산출해 그 증가분만 발행
        - 조회용 저장소는 발행 성패와 무관하게 매 주기 현재 전체 목록을 저장
    - 개선 필요 이유
        - 제거(개수 감소)를 산출하지 않음 — 설비가 PM/BM에서 빠져도 소비 측은 그 항목을 계속 보유
        - 발행 실패 시 변경 감지 기준선은 갱신되지 않는데 조회용 저장소는 갱신되어, 실시간 발행분 / 조회분 / 변경 감지 기준선 3자가 서로 어긋남
    - 개선 후
        - 변경 판정 방식을 교체해 신규·개수 변화·상태 전이·제거를 모두 변경으로 판정
        - 변경 감지 시 증가분이 아닌 현재 전체 목록을 한 번에 발행 (전체 스냅샷)
        - 전원 제거 시 빈 목록을 발행해 소비 측에 초기화 신호 전달
```

- `개선 전` · `개선 필요 이유` · `개선 후` 세 하위 항목을 이 순서로 항상 쓴다.

## 작성 규칙

- **코드 식별자 금지** — 아래는 절대 쓰지 않는다. 동작 · 역할로 풀어 쓴다.
  - 클래스 · 인터페이스 · 타입 이름 (예: `OrderService` → "주문 처리 서비스")
  - 함수 · 메서드 이름 (예: `Detect()`, `Foo.Bar()` → "변경 감지")
  - 변수 · 필드 · 속성 이름 (예: `store`, `tracker` → "조회용 저장소", "변경 감지 기준선")
  - 파일 경로 · 파일명 · 네임스페이스
- **도메인 용어는 쓴다** — 업무 약어(BM/PM), 프로토콜(REST · WS), DB 컬럼 · 테이블 이름(P_KEY), 설정값 · 수치는 그대로 둔다.
- **기능 · 의도 · 이유 · 결정 수준**으로 쓴다. 한 줄은 한 문장.
- 완료되지 않은 작업을 완료처럼 쓰지 않는다 — 진행 중이면 "진행 중", 검증 전이면 "검증 전" 을 붙인다.
